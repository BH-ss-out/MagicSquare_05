## 0. 본 단계의 위치와 책무

### 0.1 사용자 여정 3계층의 정의

| Level | 이름 | 답하는 질문 | 본 프로젝트에서의 정의 |
|---|---|---|---|
| **1** | **Epic** | *왜* 우리는 이 일을 하는가? | 본 Magic Square 작업으로 무엇을 *훈련*하고 무엇으로 그 훈련의 성공을 *판정*할 것인가에 대한 합의 |
| 2 | User Story | *누가, 무엇을, 왜* 할 수 있어야 하는가? | 학습자/호출자/검증자 관점에서의 가치 단위 시나리오 (별도 문서) |
| 3 | Task | *어떻게* 할 것인가? | 코드/테스트/리팩토링 단위의 실행 작업 (별도 문서) |

> ※ Level 간 의존 방향은 **Epic → Story → Task**의 단방향이다. Task가 Epic을 바꾸지 않으며, Story가 Epic을 흔들지 않는다. 흔드는 일이 발생한다면 그것은 Epic 자체의 합의 결함이다.

### 0.2 본 단계가 *해야 하는 것*

- 본 프로젝트의 **존재 이유**(목적, Purpose)를 4개 항목 이내로 고정한다.
- 그 목적이 **달성되었음을 판정하는 기준**(성공 기준, Success Criteria)을 *측정 가능한 형태*로 환원한다.
- 선행 문서(`01_문제_정의`의 I1~I5, `02_설계`의 D/R/FR-x, `03_프로젝트_규약_정의`의 ECB·TDD·forbidden)와의 정합성을 명시한다.

### 0.3 본 단계가 *하지 않는 것*

- **누가 어떤 동작을 수행하는지**(시나리오)는 다루지 않는다 → User Story의 책무.
- **어떻게 코드로 구현하는지**(설계/테스트/리팩토링 단위 작업)는 다루지 않는다 → Task의 책무.
- **새로운 도메인 규칙(I6, D11, R-5 등)** 을 추가하지 않는다 → `01`/`02` 단계에서 닫혔음.

## 1. Epic 진술

### 1.1 Epic Title

> **"Invariant(불변조건) 기반 사고 훈련 시스템 구축"**

### 1.2 Epic 한 문장 정의 (Single-Sentence Definition)

> *"4x4 Magic Square라는 충분히 작은 도메인을 매개로 하여, 학습자가 산출물보다 **불변조건을 먼저 정의하고, 검증을 먼저 설계하며, 계약을 먼저 고정하는** 사고 양식을 — 임의 입력에 대해 결정적·반복적·자동적으로 — 강화하도록 만드는 훈련 시스템을 구축한다."*

### 1.3 핵심 키워드 분해 (각 단어가 왜 그 자리에 있는가)

| 키워드 | 본 Epic에서의 의미 | 근거 문서 |
|---|---|---|
| **Invariant 기반** | 코드/알고리즘이 아니라 *불변조건(I1~I5)* 이 사고의 출발점이 되어야 한다 | `01_문제_정의` 5.3 |
| **사고 훈련** | 산출물의 정확성보다 **사고 양식의 형성**이 본 프로젝트의 일차 목표 | `01_문제_정의` 5.4 |
| **시스템** | 1회성 학습이 아니라, *동일 사고 양식을 반복 강화*할 수 있는 검증 가능한 구조 | `02_설계` 4.5, `03_프로젝트_규약_정의` (`.cursorrules`) |
| **구축** | 외부에서 가져오는 것이 아니라, *본 프로젝트 자체로* 이 시스템을 외부화해 만든다 | 본 보고서 |

> ※ 이 Epic은 *"마방진을 푸는 프로그램을 만든다"* 가 아니다. **마방진은 도구이며, 훈련 시스템이 산출물이다.**

> 사용자가 제시한 4개 목적을, 본 절에서 *"무엇이 충족되어야 그 목적이 달성된 것인가"* 라는 검증 가능한 형태로 환원한다.

### 2.1 목적 P1 — Invariant 중심 설계 사고 훈련

| 항목 | 내용 |
|---|---|
| 표면 진술 | *"Invariant 중심 설계 사고 훈련"* |
| 환원된 진술 | 학습자는 산출물(코드)을 작성하기 *전에* I1~I5를 외부화 가능한 형태로 진술할 수 있어야 한다. |
| 충족 증거 | 모든 도메인 테스트(`T-D-XXX`)가 *어느 Invariant를 보호하는지* docstring 또는 ID로 명시되어 있다. |
| 위반 신호 | 테스트가 어느 Invariant도 가리키지 못함. *"그냥 동작 검증"* 만 하는 테스트의 존재. |
| 근거 문서 | `01_문제_정의` 4.2/5.3, `02_설계` 1.2 (D1~D10), `03_프로젝트_규약_정의` `testing.invariant_mapping` |

### 2.2 목적 P2 — Dual-Track TDD 적용 훈련

| 항목 | 내용 |
|---|---|
| 표면 진술 | *"Dual-Track TDD 적용 훈련"* |
| 환원된 진술 | 학습자는 **Logic Track**(Domain)과 **UI Track**(Boundary)을 *분리된 RED → GREEN → REFACTOR 사이클*로 운영할 수 있어야 한다. |
| 충족 증거 | (a) `tests/entity/`와 `tests/boundary/`가 분리되어 존재. (b) Domain 테스트는 Boundary를 모르고, Boundary 테스트는 Domain을 Mock으로 다룬다. (c) 각 트랙의 첫 RED가 *프로덕션 코드보다 먼저* 커밋된다. |
| 위반 신호 | 한 테스트가 Boundary와 Domain을 동시에 검증함. Domain 테스트가 실제 I/O를 호출함. RED 없이 작성된 production 코드의 존재. |
| 근거 문서 | `02_설계` 1.5, 2.3, `03_프로젝트_규약_정의` `tdd_rules.red_phase`, `architecture.layers.*` |

### 2.3 목적 P3 — 입력/출력 계약 명확화 훈련

| 항목 | 내용 |
|---|---|
| 표면 진술 | *"입력/출력 계약 명확화 훈련"* |
| 환원된 진술 | 학습자는 모든 Public API에 대해 **입력 스키마, 출력 스키마, 실패 조건, 검증 순서**를 byte-equal 수준으로 고정할 수 있어야 한다. |
| 충족 증거 | (a) `02_설계` 0절(Frozen Contract)이 변경 없이 유지된다. (b) 표준 에러 메시지(2.4)가 byte-equal 테스트로 보호된다. (c) 검증 순서(2.2.4)가 결정적 테스트(`T-U-040`~`T-U-042`)로 보호된다. |
| 위반 신호 | 동일 입력에 두 개 이상의 합법적 출력이 가능. 에러 메시지가 환경/시간에 따라 달라짐. *"적절히/충분히"* 어휘가 계약에 등장. |
| 근거 문서 | `02_설계` 0절, 2.2, 2.4, `03_프로젝트_규약_정의` `forbidden`, `ai_behavior.honesty` |

### 2.4 목적 P4 — 설계 → 테스트 → 구현 → 리팩토링 흐름 체화

| 항목 | 내용 |
|---|---|
| 표면 진술 | *"설계 → 테스트 → 구현 → 리팩토링 흐름 체화"* |
| 환원된 진술 | 학습자는 **설계(D-x/R-x)** 를 먼저 닫고, **테스트(T-x)** 를 먼저 RED로 작성하며, **구현**은 그 RED를 GREEN으로 만드는 *최소* 변경에 한정하고, **리팩토링**은 외부 동작 보존 하에서만 수행할 수 있어야 한다. |
| 충족 증거 | (a) 커밋 이력에 RED 커밋이 GREEN 커밋보다 먼저 등장. (b) GREEN 단계 커밋에 새 테스트 추가/리팩토링이 섞여 있지 않음. (c) REFACTOR 단계 직후에도 모든 기존 테스트가 통과. |
| 위반 신호 | 테스트 없이 추가된 production 코드. GREEN 단계에서 동시에 수행된 리팩토링. REFACTOR 단계에서 외부 동작이 변경됨. |
| 근거 문서 | `03_프로젝트_규약_정의` `tdd_rules.red_phase / green_phase / refactor_phase` 전체 |

### 2.5 4개 목적의 상호 관계

| 관계 | 의미 |
|---|---|
| P1 → P2 | Invariant가 외부화되어야(P1), 어떤 Track의 어떤 RED가 어떤 Invariant를 보호하는지(P2)가 정해진다. |
| P2 → P3 | 두 Track이 분리되어야(P2), 두 Track 사이에 *어떤 계약이 흐르는가*(P3)가 명확해진다. |
| P3 → P4 | 계약이 byte-equal로 고정되어야(P3), 그 위에서 RED → GREEN → REFACTOR가 *결정적으로* 진행될 수 있다(P4). |
| P4 → P1 (회귀) | 흐름을 체화한 결과(P4)가 다시 *Invariant를 먼저 진술하는 습관*(P1)을 강화한다. |

> ※ 즉, P1은 *입력 자격*, P4는 *출력 안정성*에 해당한다. P2/P3은 *둘을 잇는 다리*이다. 네 목적은 한 사이클을 이룬다.

## 3. 성공 기준 (Success Criteria) — 측정 방법까지 함께 고정

> 사용자가 제시한 5개 성공 기준을, *어떤 도구로, 어떤 명령으로, 어떤 임계값에서, 누가* 판정하는지까지 외부화한다.
> 측정 방법이 명시되지 않은 성공 기준은 본 프로젝트에서 *성공 기준이 아니다*.

### 3.1 SC-1 — Domain Logic 95% 이상 테스트 커버리지

| 항목 | 내용 |
|---|---|
| 측정 대상 | `src/magicsquare/entity/` 및 `src/magicsquare/control/` 하위 모든 모듈 |
| 측정 도구 | `pytest --cov=src/magicsquare/entity --cov=src/magicsquare/control --cov-report=term-missing --cov-fail-under=95` |
| 임계값 | 라인 커버리지 ≥ 95%, 분기 커버리지 ≥ 90% |
| 합격 조건 | `--cov-fail-under=95` 옵션이 *exit code 0* 으로 종료 |
| 미달 시 정책 | 미커버 분기에 대해 RED 테스트를 추가 (실패 분기/엣지 우선). 임계 우회를 위한 `# pragma: no cover`는 *정당한 이유 주석*이 동반되지 않으면 금지. |
| 정합성 근거 | `02_설계` 4.4, `03_프로젝트_규약_정의` `testing.coverage` |

### 3.2 SC-2 — 입력 검증 100% 계약 테스트 통과

| 항목 | 내용 |
|---|---|
| 측정 대상 | `tests/boundary/` 하위 모든 `T-U-XXX` (계약 테스트) |
| 측정 도구 | `pytest tests/boundary/ -v` |
| 임계값 | 통과율 100% (실패/스킵 0건) |
| 합격 조건 | `T-U-001`~`T-U-074` 전체 PASS, `xfail`/`skip` 0건 |
| 미달 시 정책 | 단 한 건의 실패/스킵도 허용하지 않는다. *입력 검증은 도메인 진입의 자격 게이트*이므로 부분 통과 의미 없음. |
| 정합성 근거 | `02_설계` 2.3, 2.4, `03_프로젝트_규약_정의` `architecture.layers.boundary` |

### 3.3 SC-3 — 하드코딩 없음

| 항목 | 내용 |
|---|---|
| 측정 대상 | `src/magicsquare/` 전체 (테스트 데이터 fixture는 제외) |
| 측정 도구 | (a) `ruff check src/`, (b) 코드 리뷰, (c) 정적 grep (`rg -n "['\"]([^'\"]{20,})['\"]" src/` 등 임계 길이 문자열 탐지) |
| 정의 | *"의미 없이 코드에 박힌 리터럴 값/문자열"* 의 부재. 단, *불변 상수 모듈*(`entity/`)에 정의된 `Final` 상수의 사용은 하드코딩이 아니다. |
| 합격 조건 | (a) 도메인/규칙을 표현하는 모든 리터럴이 `entity/` 하위 상수 모듈로 외부화. (b) 테스트 메시지·에러 코드도 단일 진실 출처(SSOT)에서 import. |
| 미달 시 정책 | 하드코딩이 발견되면 즉시 상수화 후 import. *"가독성 위해 그대로 두자"* 는 합의 사유로 인정하지 않음. |
| 정합성 근거 | `03_프로젝트_규약_정의` `forbidden`(매직 넘버/문자열 항목), `02_설계` 0.3, 2.4 |

### 3.4 SC-4 — 매직 넘버 없음

| 항목 | 내용 |
|---|---|
| 측정 대상 | `src/magicsquare/` 전체 |
| 측정 도구 | `ruff check`(룰 `PLR2004` *Magic value used in comparison* 활성화), 코드 리뷰 |
| 정의 | *4(격자 크기), 16(값 상한), 34(Magic Constant), 6(출력 길이), 0(빈칸 표지) 등의 도메인 상수가 코드에 직접 박힌 형태로 등장하지 않음*. |
| 합격 조건 | 모든 도메인 상수가 `entity/` 내 `Final` 상수로 정의되고, 사용처는 import만 한다. 예: `GRID_SIZE`, `VALUE_RANGE`, `MAGIC_CONSTANT`, `RESULT_LENGTH`, `BLANK_MARKER`. |
| 미달 시 정책 | 매직 넘버가 발견되면 *해당 상수를 만들고 모든 사용처를 일괄 교체*한다. 부분 교체 금지(중간 상태가 더 위험). |
| 정합성 근거 | `03_프로젝트_규약_정의` `forbidden`(첫 항목), `02_설계` 0.3 |

> ※ SC-3과 SC-4의 차이: SC-3은 **리터럴 일반**(문자열 포함), SC-4는 **숫자에 한정된 도메인 상수**의 박힘. 두 기준은 한쪽이 다른 쪽을 흡수하지 않는다.

### 3.5 SC-5 — Invariant → Test 추적 가능 (Traceability)

| 항목 | 내용 |
|---|---|
| 측정 대상 | I1~I5 모든 Invariant |
| 측정 도구 | (a) `02_설계` 4.5 Traceability Matrix, (b) 각 테스트의 docstring/ID |
| 임계값 | I1~I5 각각이 *최소 1개 이상의 Test ID(`T-D-XXX` 또는 `T-U-XXX`)* 와 명시적으로 연결됨 |
| 합격 조건 | (a) 4.5 매트릭스의 모든 행이 비어 있지 않음. (b) 모든 테스트의 docstring 또는 함수명에 *어느 Invariant를 보호하는지* 식별 가능. (c) 역추적 체크리스트(4.5.1)의 5개 항목 모두 ✅. |
| 미달 시 정책 | Invariant ↔ Test 누락 시 *테스트를 추가*하거나 *Invariant 정의 자체를 수정*한다. 매트릭스에서만 메우는 행위(*paper-only fix*) 금지. |

### 3.6 5개 성공 기준의 합집합 의미

| 기준 | 보호하는 측면 | 부재 시 무너지는 것 |
|---|---|---|
| SC-1 | *얼마나* 테스트되었는가 (양적 충분성) | 보지 않은 분기에서 결정적 실패 발생 가능 |

## 6. 식별된 한계 및 운영 결정

### 6.1 한계

1. **Epic은 자동 검증되지 않는다.** SC-1/SC-2/SC-4는 도구로 측정 가능하지만, SC-3과 SC-5는 *코드 리뷰*가 보조해야 한다. 즉, 본 Epic은 도구만으로 닫히지 않는 *합의 영역*을 일부 포함한다.
2. **학습자의 *사고*는 직접 측정 불가하다.** 본 Epic은 *사고의 산출물*(테스트, 커밋 순서, 매트릭스)을 통해 사고를 *간접 추론*한다. 따라서 *"산출물은 만족하는데 사고는 따라오지 않은 경우"* 는 본 Epic만으로는 식별되지 않는다.
3. **비목표(NG-x)는 *지금* 닫혀 있을 뿐이다.** 본 프로젝트가 종료된 후 비목표가 가치 있는 확장이 될 수 있으나, 그 시점의 합의는 별도 Epic의 책무이다.

### 6.2 운영 결정 (선행 문서와의 충돌 해소)

| 충돌 | 결정 |
|---|---|
| `.cursorrules` `testing.coverage.minimum=80` vs **SC-1=95** | SC-1은 *Domain 한정 임계*, 80은 *전체 프로젝트 임계*. 양립한다. 다음 단계(`pyproject.toml` 작성)에서 두 옵션을 분리 측정 가능하도록 `pytest.ini_options`에 명시한다. |
| `02_설계` 4.4 *UI ≥ 85% 라인* vs **SC-2=100% 통과율** | 두 지표는 측정 *대상*이 다르다(라인 vs 통과). UI 라인 커버리지 85%는 보조 지표로 유지하되, **본 Epic의 합격 판정은 SC-2(100% 통과율) 단독**으로 한다. |
