## 0. 입출력 계약 고정 (Frozen Contract)

> 본 절은 **변경 금지** 영역입니다. 이후 모든 레이어는 이 계약 위에서 설계됩니다.

### 0.1 입력 계약

| 항목 | 규칙 | 검증 방식 |
|---|---|---|
| 형태 | `int[4][4]` (행 4, 열 4) | 행 개수 == 4 ∧ 모든 행의 열 개수 == 4 |
| 셀 값 정의역 | `0` 또는 `1..16` 정수 | `v == 0 ∨ (1 ≤ v ≤ 16)` |
| 빈칸 표기 | `0` | — |
| 빈칸 개수 | **정확히 2개** | `count(v == 0) == 2` |
| 중복 | `0`을 제외한 값 중 동일 값 2회 이상 등장 금지 | `multiset(v != 0)` 내 중복 없음 |

### 0.2 출력 계약

| 항목 | 규칙 |
|---|---|
| 반환 타입 | `int[6]` |
| 좌표 인덱싱 | **1-index** (행/열 모두 `1..4`) |
| 반환 포맷 | `[r1, c1, n1, r2, c2, n2]` |
| `(r1,c1)` 정의 | 행-우선(row-major) 스캔 시 **첫 번째**로 발견되는 빈칸의 좌표 |
| `(r2,c2)` 정의 | 행-우선 스캔 시 **두 번째**로 발견되는 빈칸의 좌표 |
| `n1, n2` 의미 | 격자에 누락된 두 숫자(둘 중 하나는 작은 수, 하나는 큰 수) |
| 순서 결정 규칙 | 조합 A: `(작은수→첫빈칸, 큰수→둘째빈칸)`을 채워 만든 격자가 마방진이면 → `n1=작은수, n2=큰수`. 그렇지 않으면 → `n1=큰수, n2=작은수` (조합 B). |
| 마방진 판정 기준 | 행 합 4개, 열 합 4개, 두 대각선 합이 모두 **34**(Magic Constant)와 같음 |

### 0.3 Magic Constant 확정

| 기호 | 값 | 유도 |
|---|---|---|
| `M` (Magic Constant) | `34` | `M = n × (n² + 1) / 2`, n=4 → `4 × 17 / 2 = 34` |

### 0.4 도메인 실패(예외) 분류표

| 코드 | 분류 | 의미 | 책임 레이어 |
|---|---|---|---|
| `E_SHAPE` | 입력 형태 오류 | 4x4가 아님 | UI Boundary |
| `E_BLANK_COUNT` | 빈칸 개수 오류 | 빈칸이 0/1/3개 이상 | UI Boundary |
| `E_VALUE_RANGE` | 값 범위 오류 | 셀 값이 `{0} ∪ {1..16}` 밖 | UI Boundary |
| `E_DUPLICATE` | 중복 오류 | `0` 제외 중복 존재 | UI Boundary |
| `E_UNSOLVABLE` | 도메인 실패 | 두 조합 모두 마방진을 만들지 못함 | Domain |
| `E_PERSISTENCE` | 저장/로드 실패 | 파일 부재/형식 오류 등 | Data |

# 1) Logic Layer (Domain Layer) 설계

## 1.1 도메인 개념 (Entities / Value Objects / Domain Services)

### 1.1.1 Entity

| 이름 | 책임 (SRP) | 보유 상태 |
|---|---|---|
| `Board` | 4x4 격자의 **현재 상태**를 보유하고, 셀 단위 조회·치환의 단일 진입점 역할만 수행 | 4x4 정수 배열 1개 |

> ※ `Board`는 *판정* 책임을 갖지 않는다. 판정은 Domain Service가 수행한다.

### 1.1.2 Value Object (불변)

| 이름 | 책임 | 동등성 기준 |
|---|---|---|
| `Coordinate` | 1-index `(row, col)` 한 쌍 표현 | `(row, col)` 전체 일치 |
| `BlankPair` | 행-우선 스캔 순서로 정렬된 **빈칸 좌표 2개** 묶음 | `(first, second)` 일치 |
| `MissingPair` | 누락된 **두 숫자**의 묶음 (오름차순 정렬 보장) | `(small, large)` 일치 |
| `MagicConstant` | 상수 `34` (불변) | 값 일치 |
| `FillPlan` | 빈칸에 어떤 숫자를 어떤 순서로 채울지에 대한 계획 (`first→x, second→y`) | `(x, y)` 일치 |
| `MagicResult` | `int[6]` 출력 산출물 | 6개 원소 전체 일치 |

### 1.1.3 Domain Service (무상태)

| 이름 | 책임 (단 하나의) |
|---|---|
| `BlankFinder` | `Board`에서 빈칸 좌표를 행-우선 순서로 정확히 2개 찾아 `BlankPair` 반환 |
| `MissingNumberFinder` | `Board`에서 `1..16` 중 등장하지 않은 숫자 2개를 `MissingPair`(오름차순)로 반환 |
| `MagicSquareJudge` | 채워진 `Board`가 마방진 불변조건(행/열/대각 합 = 34)을 만족하는지 **boolean**으로 판정 |
| `FillPlanResolver` | 두 후보 조합(A/B) 중 마방진이 되는 조합을 결정하여 `FillPlan` 반환 |
| `MagicResultAssembler` | `BlankPair` + `FillPlan` → `MagicResult(int[6])` 조립 |

> ※ 각 서비스는 **다른 서비스의 내부 동작을 모른다**(낮은 결합도). 의존은 입력/반환 VO에 한정.

## 1.2 도메인 불변조건 (Invariants)

> 선행 문서의 I1~I5를 본 레이어의 *검증 가능한 술어*로 환원한다.

| ID | Invariant | 술어 (검증 가능) | 보호 주체 |
|---|---|---|---|
| **D1** | 형태 불변성 | `rows(Board)==4 ∧ ∀r: cols(Board[r])==4` | UI Boundary 진입 시 |
| **D2** | 정의역 불변성 | `∀cell ∈ Board: cell == 0 ∨ 1 ≤ cell ≤ 16` | UI Boundary 진입 시 |
| **D3** | 유일성 불변성 | `multiset({cell ∈ Board : cell != 0})` 내 중복 없음 | UI Boundary 진입 시 |
| **D4** | 빈칸 카디널리티 | `count(cell == 0) == 2` | UI Boundary 진입 시 |
| **D5** | 누락 카디널리티 | `\|{1..16} \ filledValues\| == 2` | `MissingNumberFinder` |
| **D6** | Magic Constant 균일성 | `∀ row r: sum(r)==34 ∧ ∀ col c: sum(c)==34 ∧ sum(diag↘)==34 ∧ sum(diag↙)==34` | `MagicSquareJudge` |
| **D7** | 해의 결정성 | 동일 입력에 대해 항상 동일 `MagicResult` 반환 | 전체 도메인 |
| **D8** | 좌표 인덱싱 일관성 | 출력 좌표는 1-index, 행-우선 스캔 순서를 따름 | `MagicResultAssembler` |
| **D9** | 순서 규칙 | 조합 A가 마방진이면 `(small→first, large→second)`, 아니면 조합 B | `FillPlanResolver` |
| **D10** | 풀이 가능성 | 적어도 하나의 조합(A 또는 B)이 마방진을 만든다고 보장되지 않으면 `E_UNSOLVABLE` 발생 | `FillPlanResolver` |

> ※ D1~D4는 *입력 자격*, D5는 *유도 가능성*, D6은 *마방진 본질*, D7~D9는 *출력 안정성*, D10은 *실패 식별성*을 각각 책임진다.

## 1.3 핵심 유스케이스 (Domain 관점)

### 1.3.1 유스케이스 목록

| UC-ID | 이름 | 1-line 설명 |
|---|---|---|
| `UC-D1` | 빈칸 위치 결정 | `Board` → `BlankPair` (행-우선 2개) |
| `UC-D2` | 누락 숫자 결정 | `Board` → `MissingPair` (오름차순 2개) |
| `UC-D3` | 마방진 판정 | `Board(빈칸 없음)` → `boolean` |
| `UC-D4` | 두 조합 시도 후 채움 계획 결정 | `Board + BlankPair + MissingPair` → `FillPlan` 또는 `E_UNSOLVABLE` |
| `UC-D5` | 결과 조립 | `BlankPair + FillPlan` → `MagicResult(int[6])` |
| `UC-D6` | 도메인 오케스트레이션 | `Board` → `MagicResult` (UC-D1~D5 직렬 실행) |

### 1.3.2 유스케이스 흐름 (UC-D6, 직렬)

```
Board
  └─[UC-D1]─→ BlankPair
  └─[UC-D2]─→ MissingPair
                  └─[UC-D4]─→ (조합 A로 채운 Board) ─[UC-D3]─→ boolean
                              (boolean==false 시) (조합 B로 채운 Board) ─[UC-D3]─→ boolean
                              (둘 다 false 시) → E_UNSOLVABLE
                              결과: FillPlan
  └─[UC-D5]─→ MagicResult(int[6])
```

> ※ 흐름은 **단방향**이며, 후속 단계는 선행 단계의 출력만을 사용한다(낮은 결합도).

## 1.4 Domain API (내부 계약)

> 메서드 시그니처 수준의 의사 표기(코드 아님). 모든 메서드는 **입력 / 반환 / 실패조건**이 명시된다.

| Service | Method (의사 시그니처) | 입력 | 반환 | 실패 조건 |
|---|---|---|---|---|
| `BlankFinder` | `findBlanks(board: Board) → BlankPair` | 빈칸이 정확히 2개인 `Board` | 행-우선 정렬된 `BlankPair` | 빈칸 개수 ≠ 2 → 도메인 가정 위반 (사전조건 위반: `Precondition violated`) |
| `MissingNumberFinder` | `findMissing(board: Board) → MissingPair` | `1..16` 중 14개가 들어있는 `Board` | 오름차순 `MissingPair` | 누락 개수 ≠ 2 → 사전조건 위반 |
| `MagicSquareJudge` | `isMagic(board: Board) → boolean` | **빈칸 없는** 4x4 `Board` | `true` / `false` | 빈칸이 1개 이상 존재 → 사전조건 위반 |
| `FillPlanResolver` | `resolve(board, blanks, missing) → FillPlan` | `Board`, `BlankPair`, `MissingPair` | 마방진을 만드는 `FillPlan` | 두 조합 모두 비-마방진 → `E_UNSOLVABLE` |
| `MagicResultAssembler` | `assemble(blanks, plan) → MagicResult` | `BlankPair`, `FillPlan` | `int[6]` (1-index 좌표) | 좌표가 `1..4` 범위 밖 → 사전조건 위반 |

> 사전조건 위반(Precondition violated)은 **호출자 책임**이며, UI Boundary가 사전에 차단해야 한다.
> 따라서 도메인은 *방어적 검증*을 중복으로 하지 않는다. 단, 디버그 모드 가드(assert)는 허용한다.

### 1.4.1 채움(Fill) 시뮬레이션 규칙

> `FillPlanResolver` 내부의 *판정 보조* 절차이며, 외부에 노출되지 않는다.

| 단계 | 동작 |
|---|---|
| F-1 | `FillPlan_A = (first→missing.small, second→missing.large)` 생성 |
| F-2 | `Board_A = Board`의 빈칸을 `FillPlan_A`로 채운 가상 격자 |
| F-3 | `MagicSquareJudge.isMagic(Board_A)` 호출 |
| F-4 | `true`이면 `FillPlan_A` 반환, 종료 |
| F-5 | `FillPlan_B = (first→missing.large, second→missing.small)` 생성 |
| F-6 | `Board_B = Board`의 빈칸을 `FillPlan_B`로 채운 가상 격자 |
| F-7 | `MagicSquareJudge.isMagic(Board_B)` 호출 |
| F-8 | `true`이면 `FillPlan_B` 반환, 종료 |
| F-9 | 둘 다 `false` → `E_UNSOLVABLE` 예외 |

# 3) Data Layer 설계

## 3.1 목적 정의

> Data Layer는 **DB가 아니라**, "저장/로드 인터페이스를 분리해 두면 *나중에* 메모리 ↔ 파일을 교체할 수 있다"는 점을 학습하기 위한 **얇은 경계**다.

### 3.1.1 학습 목적

| 목적 ID | 학습 포인트 |
|---|---|
| `DP-1` | 도메인은 *어떻게 저장되는가*를 모르도록 추상화한다 (의존성 역전, DIP) |
| `DP-2` | 메모리 구현으로 시작해 파일 구현으로 교체했을 때 **모든 도메인 테스트가 통과**해야 한다 |
| `DP-3` | 저장 형식 변경(JSON → CSV 등)이 도메인을 흔들지 않는다 |

### 3.1.2 범위 (의도적 축소)

| 포함 | 미포함 |
|---|---|
| 입력 행렬 1건 저장 / 단일 ID 로드 | 동시성 / 트랜잭션 / 인덱스 |
| 실행 결과(`int[6]`) 저장(선택) | 페이지네이션 / 쿼리 |
| 메모리 / 파일 구현 교체 가능성 | 외부 DB / 네트워크 / 캐싱 |

---

## 3.2 인터페이스 계약 (의사 시그니처, 코드 X)

### 3.2.1 `MatrixRepository`

| Method | 입력 | 반환 | 실패 조건 |
|---|---|---|---|
| `save(id: string, matrix: int[4][4]) → void` | 비어있지 않은 ID, 4x4 행렬 | 없음 | ID 빈 문자열 → `E_PERSISTENCE`<br>형태 위반 → `E_PERSISTENCE` |
| `load(id: string) → int[4][4]` | 존재하는 ID | 4x4 행렬 | ID 부재 → `E_PERSISTENCE`<br>역직렬화 실패 → `E_PERSISTENCE` |
| `exists(id: string) → boolean` | 임의 ID | `true` / `false` | 없음 (예외 없이 false 반환) |
| `delete(id: string) → boolean` | 임의 ID | 삭제했으면 `true` | I/O 실패 시 `E_PERSISTENCE` |

### 3.2.2 `ResultRepository` (선택, `int[6]` 저장)

| Method | 입력 | 반환 | 실패 조건 |
|---|---|---|---|
| `saveResult(id: string, result: int[6]) → void` | 비어있지 않은 ID, 6원소 배열 | 없음 | 길이 ≠ 6 → `E_PERSISTENCE` |
| `loadResult(id: string) → int[6]` | 존재하는 ID | 6원소 배열 | ID 부재 / 형태 위반 → `E_PERSISTENCE` |

### 3.2.3 불변조건 (Data Layer)

| ID | 규칙 |
|---|---|
| `R-1` | `save → load` 라운드트립은 **byte-equal한 행렬**을 복원해야 한다 |
| `R-2` | 형태가 4x4가 아닌 행렬은 **저장 자체가 거부**된다 |
| `R-3` | 동일 ID로 재-`save`하면 **덮어쓰기**(idempotent하지 않음)이며, 직전 값은 폐기된다 |
| `R-4` | `load`는 *항상* 4x4 행렬을 반환하거나 예외를 던진다 (null 금지) |

---

## 3.3 구현 옵션 비교 — 메모리 vs 파일

| 비교 축 | 옵션 A: InMemory | 옵션 B: File (JSON) |
|---|---|---|
| 영속성 | 프로세스 내 한정 | 프로세스 종료 후에도 유지 |
| 의존성 | 표준 자료구조만 | 파일 시스템 / 직렬화 라이브러리 |
| 테스트 용이성 | 매우 높음 (격리) | 보통 (임시 디렉터리 필요) |
| 실패 케이스 | 거의 없음 | 파일 부재 / 권한 / 형식 오류 |
| 학습 효과 | DIP/계약 학습 시작점 | 직렬화 / I/O 예외 처리 학습 |
| 구현 난이도 | 낮음 | 중간 |

### 3.3.1 추천안

> **권장: 옵션 A(InMemory)를 1차 구현**, 이후 **옵션 B(JSON 파일)를 동일 인터페이스로 교체**하여
> *동일한 도메인/UI 테스트가 모두 그대로 통과*함을 검증한다.

**이유 (검증 가능한 형태):**

| 근거 ID | 근거 |
|---|---|
| `J-1` | 학습 목표가 *영속성 자체*가 아니라 *경계 분리*이므로, 1차 구현은 외란 요소(I/O 예외)를 배제한 InMemory가 적절 |
| `J-2` | InMemory → File 교체 시 **테스트 코드 변경 0건**이어야 한다는 명제를 검증 가능한 회귀 보호 규칙으로 만들 수 있음 |
| `J-3` | JSON 형식은 4x4 정수 배열의 사람-검증 가능성이 가장 높음 (CSV는 행/열 차원 모호) |

> 테스트 ID는 `T-R-XXX`. 모든 테스트는 **InMemory와 File 양쪽에서 동일하게** 통과해야 한다(R-1 보호).

### 3.4.1 정합성 테스트

| Test ID | 케이스 | 검증 내용 |
|---|---|---|
| `T-R-001` | save → load 라운드트립 | 동일 행렬 byte-equal 복원 (R-1) |
| `T-R-002` | save → exists | 저장 직후 `exists == true` |

# 4) Integration & Verification (통합 및 검증)

## 4.1 통합 경로 정의

### 4.1.1 의존성 방향 (Clean Architecture)

```
[ Caller / Test Driver ]
            │
            ▼
[ Screen Layer (Boundary) ]   ── E_SHAPE / E_VALUE_RANGE / E_BLANK_COUNT / E_DUPLICATE 차단
            │
            ▼
[ Application Service (Optional Orchestrator) ]
            │
            ├─────────────────────────────┐
            ▼                             ▼
[ Domain (Logic Layer) ]         [ Data Layer (Repository) ]
   - BlankFinder                    - MatrixRepository
   - MissingNumberFinder            - ResultRepository (선택)
   - MagicSquareJudge
   - FillPlanResolver
   - MagicResultAssembler
```

### 4.1.2 의존성 규칙 (변경 금지)

| 규칙 ID | 규칙 |
|---|---|
| `A-1` | 의존성 화살표는 **위에서 아래로만** 흐른다. Domain은 Boundary/Data를 *알지 못한다*. |
| `A-2` | Boundary와 Data는 서로를 *직접* 참조하지 않는다. (Application이 매개) |

> **마무리 진술**
>
> 본 설계는 *"무엇을 구현할 것인가"*가 아니라 *"무엇이 검증되어야 하는가"*를 먼저 고정한다.
> 모든 술어(D-x, R-x)와 테스트(T-x)는 **단일한 Invariant** 또는 **단일한 계약**만을 보호하며,
> 어느 한 줄의 production 코드도 *그 보호망 바깥*에서 작성되어서는 안 된다.
>
> 이 문서가 합의되는 순간, RED 테스트는 *작성될 준비가 된 상태*가 된다.
