## 0. 본 단계의 위치와 책무

### 0.1 Level 1 → Level 2의 전이

| 구분 | Level 1 (Epic) | Level 2 (User Journey, 본 문서) |
|---|---|---|
| 답하는 질문 | *왜 우리는 이 일을 하는가?* | *누가, 어떤 시간 순서로, 어떤 사고를 통과하며 이 일을 하는가?* |
| 산출 단위 | 4개 목적(P1~P4) + 5개 성공 기준(SC-1~SC-5) | 1명의 Persona + 5개 Step의 시간 축 여정 |
| 시간 차원 | 없음 (목표는 시간에 무관) | 있음 (Step은 *순서를 가진* 사고 단위) |
| 결과 형태 | 평면적 진술 (모든 목적이 동시에 성립) | 순차적 진술 (선행 Step이 닫혀야 후속 Step이 열림) |

> ※ 즉, 본 단계는 Level 1을 *시간 축 위에 다시 펼친* 보고서이다. 동일한 목적·기준을 *언제, 어떤 인지 상태로* 부딪히는지 외부화한다.

### 0.2 본 단계가 *해야 하는 것*

- Persona를 단일 인격으로 고정하고, 그 페르소나가 *어울리지 않는* 안티패턴(Anti-Persona)도 함께 외부화한다.
- 5개 Step 각각에 **활동 / 인지 상태 / 산출물 / 보호하는 목적·Invariant / 위반 신호 / 전이 조건**을 부여한다.
- Step 간 *역행(Backtracking)* 가능 여부를 결정적으로 닫는다.

### 0.3 본 단계가 *하지 않는 것*

- *어떤 코드 파일에 어떤 함수를 추가하는가* 같은 단위 작업 분해 → Level 3(Task)의 책무.
- *어떤 commit을 어떤 PR로 묶는가* 같은 작업 흐름 관리 → 본 프로젝트 범위 밖.
- *새로운 Persona 추가* — 본 프로젝트의 학습 단위는 단일 페르소나로 고정.

## 1. Persona (페르소나)

### 1.1 페르소나 요약

> **이름(역할):** *학습자(L)*
> **한 문장 정의:** *소프트웨어 개발을 학습 중이며, TDD 사이클과 Clean Architecture의 경계를 *이해하려고 노력하는 단계*에 있는 개인.*

### 1.2 페르소나의 3개 핵심 특성

| 특성 ID | 표면 진술 | 환원된 진술 (검증 가능) | 충족 증거 |
|---|---|---|---|
| **L-1** | 소프트웨어 개발 학습자 | 코드 산출 능력은 보유하나, *"산출 이전에 무엇을 합의해야 하는가"* 는 아직 불완전한 단계. | 표면 정의 ↔ 개선된 정의 사이의 차이를 *스스로* 식별할 수 있다. |
| **L-2** | TDD 훈련 중 | RED → GREEN → REFACTOR의 3단계를 *분리된 단계*로 인식하고, 각 단계의 *해서는 안 되는 행위*까지 함께 익히는 중. | RED 없이 production 코드를 작성하지 않으며, GREEN 도중 리팩토링을 동시에 수행하지 않는다. |
| **L-3** | Clean Architecture 이해 중 | 폴더 분리가 아니라 *의존 방향*이 본질임을 받아들이는 중. ECB 3계층 사이의 의존이 *안쪽 방향*임을 코드 작성 시점에 의식할 수 있다. | `entity/`가 `boundary/`를 import하지 않는다. *"폴더만 나누면 됨"* 사고가 발견되면 즉시 교정한다. |

### 1.3 페르소나가 *아닌* 사람 (Anti-Persona)

> 본 여정에 어울리지 않는 사고 양식을 명시함으로써, 학습 도중 페르소나가 무너지는 신호를 사전 식별한다.

| Anti ID | 안티패턴 진술 | 등장 신호 (위반 신호) |
|---|---|---|
| **A-1** | *산출물 중심 사고자* — *"답을 빨리 만들고 싶다"* 가 첫 충동 | I1~I5를 외부화하기 전에 알고리즘부터 구상한다. |
| **A-2** | *테스트 후행자* — *"동작하면 나중에 테스트를 붙이겠다"* 라는 사고 | RED 없이 작성된 production 코드가 발견된다. |
| **A-3** | *폴더 분리주의자* — Clean Architecture를 폴더 구조로만 이해 | `entity/`에서 `boundary/`나 외부 라이브러리를 import한다. |
| **A-4** | *충분주의자* — *"적절히/충분히 동작한다"* 어휘를 사용 | 계약 진술에 *"적절히"*, *"보통은"*, *"대부분"* 어휘가 등장한다. |
| **A-5** | *회귀 무관심자* — *"새 기능 추가하다 기존 테스트 깨지면 약화시키면 됨"* | 기존 단언이 약화되거나 `xfail`/`skip`이 사후적으로 추가된다. |

> ※ Anti-Persona의 등장 신호 1건 이상 발견 시, 해당 Step은 *전진하지 못하며*, 8.2의 회귀 정책에 따라 *역행* 처리된다.

## 2. Journey 개관

### 2.1 5-Step Journey 한눈에 보기

```
[Step 1: 문제 인식]
  "마방진을 구현한다"가 아니라 "판정 체계를 정의한다"로 인지 전환
        │
        ▼
[Step 2: 계약 정의]
  입력 스키마 / 출력 스키마 / 예외 정책을 byte-equal 수준으로 고정
        │
        ▼
[Step 3: Domain 분리]
  BlankFinder / MissingNumberFinder / MagicSquareValidator / Solver
  (인지 단위 4개 ↔ 구현 단위 5개 매핑)
        │
        ▼
[Step 4: Dual-Track 진행]
  ┌─────────────────────┬─────────────────────┐
  │  UI Track RED       │  Logic Track RED    │  (병렬)
  │       │             │       │             │
  │  GREEN 최소 구현     │  GREEN 최소 구현    │
  └─────────────────────┴─────────────────────┘
                  │
              REFACTOR 통합 정리
                  │
                  ▼
[Step 5: 회귀 보호]
  엣지 / 입력 오류 / 조합 실패 케이스 추가 → 변경 금지 영역(FR-1~FR-7) 봉인
```

### 2.2 Step 간 의존 관계

| 전이 | 의존 형태 | 의미 |
|---|---|---|
| Step 1 → 2 | **강(strong)** | I1~I5가 외부화되지 않은 상태에서 계약은 진술 불가능. |
| Step 2 → 3 | **강** | 입출력 계약이 byte-equal로 고정되지 않은 상태에서 Domain 분리는 *근거 없는 분해*가 된다. |
| Step 3 → 4 | **강** | 4개(인지) / 5개(구현) 서비스의 책임이 명시되지 않은 상태에서는 RED를 *어디에 작성할지* 결정 불가. |
| Step 4 → 5 | **약(soft)** | Step 4가 일부만 GREEN이어도 Step 5의 *그 부분에 대한* 회귀 보호는 시작 가능. (단, 미완 영역에 대한 회귀 보호는 의미 없음) |
| Step 5 → 종료 | **약** | 회귀 보호는 *지속적 활동*이며 1회 완수로 닫히지 않는다. SC-1~SC-5 모두 충족 시 Epic 완료로 간주. |

> ※ 강한 의존은 *역행 가능*하지만 (8.2 참조), 그것은 *선행 단계의 합의 결함*을 의미하며 비용이 크다.

## 3. Step 1 — 문제 인식

> *"마방진을 구현한다"* 가 아니라, *"임의의 4x4 배치에 대해 마방진 여부를 결정적으로 판정하는 체계를 정의한다"* 로의 인지 전환.

### 3.1 6종 키 분석

| 키 | 내용 |
|---|---|
| **활동** | 표면 정의(*"4x4 격자에 1~16을 배치하는 프로그램"*)의 *부족함*을 식별. 그 부족함이 *주체·대상·속성·산출* 4축 중 어느 것을 누락했는지 분해. I1~I5 5개 불변조건을 외부화. |
| **인지 상태** | *산출물 중심 사고* → *검증 중심 사고* 로의 전환. *"무엇을 만들 것인가"* 라는 질문 자체가 *"어떻게 옳음을 판별할 것인가"* 라는 질문에 비해 *후행한다*는 감각의 형성. |
| **산출물** | `01_문제_정의.md` 5.2(개선된 정의), 5.3(I1~I5 표). |
| **보호하는 Epic 목적** | **P1** (Invariant 중심 설계 사고 훈련) |
| **보호하는 Invariant** | I1~I5 *전체* (이 단계는 모든 Invariant의 외부화 자체) |
| **위반 신호 (Anti-Pattern)** | (a) *"마방진을 풀어야지"* 같은 산출물 중심 어휘의 재등장. (b) I1~I5 중 일부가 누락된 채 다음 단계로 진입. (c) 산출 알고리즘을 먼저 떠올리고 그 알고리즘에 맞춰 Invariant를 *역으로* 진술하는 행위 (Anti-Persona A-1). |
| **다음 단계 전이 조건** | I1~I5가 *각각 한 문장의 검증 가능한 술어*로 외부화되어 `01_문제_정의` 5.3 표에 기재됨. 표면 정의와 개선된 정의의 차이가 *학습자 본인의 언어로* 진술 가능. |

### 3.2 학습자가 이 Step에서 부딪히는 *전형적 함정*

| 함정 | 등장 양상 | 처리 |
|---|---|---|
| *"마방진은 그냥 만드는 거 아닌가?"* | 표면 정의로 충분하다고 느끼는 인지 단축 | `01_문제_정의` 2.1 (가정된 답) → 2.2 (드러나는 불편함)의 동선을 *순서대로* 다시 통과 |
| *"부분 정답이라는 게 뭔가요?"* | 부분 위반/전체 위반의 구분 부재 | I1~I4 위반을 *서로 다른 종류*로 다루도록 하는 합의가 없으면 본 Step은 미완 |
| *"매번 같은 결과가 나오는 게 당연한 거 아닌가요?"* | 결정성(I5)이 *암묵적 전제*로 다뤄짐 | I5를 *명시적 검증 항목*으로 끌어올려 외부화 |

## 4. Step 2 — 계약 정의

> 입력 스키마 · 출력 스키마 · 예외 정책을 *byte-equal 수준*에서 고정.

### 4.1 6종 키 분석

| 키 | 내용 |
|---|---|
| **활동** | (a) 입력 스키마 정의 (행/열 차원, 셀 정의역, 빈칸 표기·개수, 중복 정책). (b) 출력 스키마 정의 (`int[6]` 형식, 1-index 좌표, 순서 결정 규칙). (c) 예외 정책 정의 (`E_SHAPE`/`E_BLANK_COUNT`/`E_VALUE_RANGE`/`E_DUPLICATE`/`E_UNSOLVABLE`/`E_PERSISTENCE` 6종 코드, 표준 메시지, 검증 순서). |
| **인지 상태** | *모호함을 견디지 못하는 감각의 형성*. *"적절히/보통은/대개"* 어휘가 등장하면 즉시 *"정확히 무엇이?"* 로 환원하려는 반사. *동일 입력에 두 출력이 합법적인 상태*를 *결함*으로 인식. |
| **산출물** | `02_설계.md` 0절(Frozen Contract), 2.2(Input/Output/Error Schema), 2.2.4(검증 순서), 2.4(표준 에러 메시지 표). |
| **보호하는 Epic 목적** | **P3** (입력/출력 계약 명확화 훈련) — 부수적으로 P1(I1·I2·I3가 입력 계약으로 환원됨), P4(계약이 고정되어야 RED가 가능). |
| **보호하는 Invariant / 술어** | I1→D1, I2→D2, I3→D3, (입력 빈칸)→D4, (오름차순 누락)→D5. 본 Step은 이 5개 술어가 *byte-equal로 외부 검증 가능*하도록 만든다. |
| **위반 신호** | (a) 검증 순서가 모호함 → 동일 입력의 에러 코드가 *환경 의존*으로 변함. (b) 에러 메시지가 *입력 데이터(셀 값 등)를 포함* → 결정성·보안 모두 위반 (`02_설계` M-2). (c) *"적절한 에러 메시지를 던진다"* 같은 어휘 (Anti-Persona A-4). |
| **다음 단계 전이 조건** | 모든 계약 항목이 *byte-equal로 표/표준 문구*에 기재됨. 동일 입력에 두 출력이 합법적인 경로가 0건. 표준 에러 메시지 5개가 *정확한 영어 1문장 + 마침표*로 고정. |

### 4.2 *왜 이 Step이 Step 1보다 *늦게* 와야 하는가*

- 계약은 *불변조건의 외화*이다. I1~I5가 정해지지 않은 상태에서 작성된 계약은 *근거 없는 자유 선택의 집합*이 된다.
- 따라서 Step 1 → Step 2의 의존은 *강한 의존*이며, 만약 Step 2 도중에 *"이 술어가 정말 맞나?"* 의문이 들면 즉시 Step 1로 역행한다 (8.2 참조).

### 4.3 학습자가 이 Step에서 부딪히는 *전형적 함정*

| 함정 | 등장 양상 | 처리 |
|---|---|---|
| *"메시지는 그냥 의미만 통하면 되는 거 아니에요?"* | byte-equal의 필요성 부정 | 표준 메시지가 *회귀 보호 대상*임을 합의 (`02_설계` 4.3.1 FR-5). 메시지 한 글자 변경 = 깨질 테스트 수의 정량적 시사. |
| *"검증을 어느 순서로 해도 결과는 같지 않나요?"* | 검증 순서의 결정성 부재 | 동일 입력에 *형태 + 범위 + 빈칸* 세 위반이 동시 존재할 때 *어느 코드가 반환되는가*에 대한 답이 *순서로만* 정해진다는 사실의 외부화 (`02_설계` 2.2.4). |

## 5. Step 3 — Domain 분리

> Domain Service 4개(인지 단위) ↔ 5개(구현 단위)의 매핑을 동시에 외부화.

### 5.1 6종 키 분석

| 키 | 내용 |
|---|---|
| **활동** | 학습자의 인지 단위로 4개 서비스를 외부화: **BlankFinder / MissingNumberFinder / MagicSquareValidator / Solver**. 그 후 `02_설계` 1.1.3의 *구현 단위 5개*와의 매핑을 명시. |
| **인지 상태** | *책임의 분해*와 *의존의 방향* 사이에서 SRP를 견디는 인내. *"한 클래스가 빈칸도 찾고 누락도 찾고 판정도 하면 편하지 않을까?"* 라는 충동을 식별하고 거부. |
| **산출물** | `02_설계.md` 1.1(개념), 1.4(Domain API), `src/magicsquare/entity/`·`control/`의 폴더 구조 (`03_프로젝트_규약_정의` `file_structure.tree` 일치). |
| **보호하는 Epic 목적** | **P2**의 *Logic Track* 측 사전 정의. 후속 Step 4의 RED가 *어디에 작성될지*를 본 Step이 결정. |
| **보호하는 Invariant / 술어** | D6(MagicSquareValidator), D9·D10(Solver), D5(MissingNumberFinder), D4·D8(BlankFinder). |
| **위반 신호** | (a) 한 서비스가 두 책임 보유. (b) `entity/`가 `boundary/`나 외부 라이브러리(`requests`, `pathlib` 등 부수 효과 라이브러리)를 import (Anti-Persona A-3). (c) Solver 내부에 직접 I/O가 박힘 (`forbidden`의 *비즈니스 로직 내 I/O* 항목 위반). |
| **다음 단계 전이 조건** | 4개(인지) ↔ 5개(구현) 매핑표가 합의됨. 각 서비스의 *입력 / 반환 / 실패 조건*이 `02_설계` 1.4에 기재됨. ECB 의존 방향(`boundary → control → entity`)이 본 Step의 산출물에 위반 0건. |

### 5.2 인지 단위(4) ↔ 구현 단위(5) 매핑표

> 학습자의 머릿속 분해는 *4개로 충분*하다. 그러나 SRP에 따른 *구현 분해*는 5개로 더 잘게 쪼개진다.
> 본 매트릭스는 *"인지 단위와 구현 단위가 1:1이 아닐 수 있다"* 는 학습 가치 자체를 외부화한다.

| 학습자의 인지 단위 (사용자 제시 4개) | 구현 단위 (`02_설계` 1.1.3 기준 5개) | 매핑 형태 | 주요 책임 |
|---|---|---|---|
| **BlankFinder** | `BlankFinder` | 1 : 1 | 행-우선 스캔으로 빈칸 좌표 2개를 `BlankPair`(1-index)로 반환 |
| **MissingNumberFinder** | `MissingNumberFinder` | 1 : 1 | `1..16` 중 누락 숫자 2개를 `MissingPair`(오름차순)로 반환 |
| **MagicSquareValidator** | `MagicSquareJudge` | 1 : 1 (이름 차이) | 빈칸 없는 `Board`가 행/열/대각 합 = 34인지 `boolean`으로 판정 |
| **Solver** | `FillPlanResolver` + `MagicResultAssembler` | 1 : 2 (인지 단위가 두 구현을 묶음) | 두 조합(A/B) 중 마방진 조합 결정 → `int[6]` 조립까지 일괄 |

### 5.3 *왜 인지 단위와 구현 단위가 다른가*

| 측면 | 학습자 인지 단위 (4개) | 구현 단위 (5개) | 차이의 의미 |
|---|---|---|---|
| 기준 | *"이 작업은 머릿속에서 한 덩어리로 다뤄지는가?"* | *"이 책임은 SRP 위반 없이 한 함수/클래스로 둘 수 있는가?"* | 인지의 단위와 단일 책임의 단위는 *서로 다른 축*이다. |
| Solver의 경우 | 학습자에게 *"풀이"* 는 한 덩어리 | "조합 결정"과 "결과 조립"은 SRP상 분리해야 함 | 인지 단위 1개가 구현 단위 2개로 *내부 분해* 됨 |
| Validator vs Judge | 학습자는 *"검증한다"* 라는 동사로 통칭 | 도메인 코드는 *"판정한다(judge)"* — *명사화된 결정 행위* | 동일 책임에 대한 *어휘의 정밀화* |

> ※ 본 Step의 학습 핵심은 *"머릿속 분해가 곧 코드 분해는 아니다"* 라는 명제의 체화이다. 4와 5의 차이를 *불편하게 느끼는 감각*이 본 Step의 통과 여부를 가른다.

### 5.4 ECB 계층 매핑

| 인지 단위 | 소속 ECB 계층 | 근거 |
|---|---|---|
| BlankFinder | `entity/` | 도메인 규칙 자체 (좌표·빈칸 정의) |
| MissingNumberFinder | `entity/` | 도메인 규칙 자체 (`1..16` 정의역) |
| MagicSquareValidator | `entity/` | I4(합 균질 불변성)의 직접 술어 |
| Solver | `control/` | 두 조합 시도·조립이 *유스케이스 흐름 조율* (`02_설계` UC-D6) |

> ※ *Solver*만 `control/`에 속하는 이유: 그 책임이 *순수 도메인 규칙*이 아니라 *유스케이스의 흐름*이기 때문이다 (`03_프로젝트_규약_정의` `architecture.layers.control.responsibilities`).

## 6. Step 4 — Dual-Track 진행

> UI Track RED ↔ Logic Track RED를 *병렬로* 작성, 각자 GREEN 최소 구현, 최종 REFACTOR로 통합.

### 6.1 6종 키 분석

| 키 | 내용 |
|---|---|
| **활동** | (a) UI Track RED: `tests/boundary/test_*.py`에 `T-U-XXX` 작성, Domain은 Mock으로 가정. (b) Logic Track RED: `tests/entity/test_*.py`·`tests/control/test_*.py`에 `T-D-XXX` 작성. (c) 각 트랙 GREEN: *현재 RED만* 통과시키는 최소 production 코드. (d) REFACTOR: 두 트랙의 GREEN이 모두 안정된 후, 외부 동작 보존 하에 중복 제거·명명 정리·계층 정리. |
| **인지 상태** | *두 트랙의 시간 동기화*와 *각 트랙의 격리* 사이의 균형. 한 트랙이 막혀도 다른 트랙이 진행 가능하다는 감각. RED 단계의 *실패 메시지 자체*를 *위반 식별 정보*로 사용하는 습관. |
| **산출물** | `tests/entity/`·`tests/control/`·`tests/boundary/` 각각의 RED→GREEN 커밋 이력. `src/magicsquare/{entity,control,boundary}/`의 production 코드. |
| **보호하는 Epic 목적** | **P2** (Dual-Track TDD), **P4** (RED→GREEN→REFACTOR 흐름). |
| **보호하는 Invariant / 술어** | I1~I5 *전체*. UI Track은 D1~D4, Logic Track은 D5~D10을 각각 보호. |
| **위반 신호** | (a) 한 RED가 두 트랙을 동시에 검증 (Boundary 테스트 안에 실제 Domain 호출이 있음). (b) GREEN 도중 동시 리팩토링 — `03_프로젝트_규약_정의` `tdd_rules.green_phase.must_not` 직접 위반. (c) RED 없이 작성된 production 코드 (Anti-Persona A-2). (d) REFACTOR 도중 외부 동작 변경 — `tdd_rules.refactor_phase.must_not` 위반. |
| **다음 단계 전이 조건** | (a) 두 트랙 각각 RED → GREEN → REFACTOR가 *최소 1 사이클씩* 완수. (b) 모든 신규 테스트의 docstring/ID가 *어느 Invariant·D-x 술어를 보호하는지* 명시. (c) `pytest`에서 *전부 PASS*. |

### 6.2 Dual-Track의 시간 모델

```
시간 →
                  ┌─ UI Track ─────────────────────────────────┐
                  │  RED (T-U-001)                            │
                  │     ▼                                     │
                  │  GREEN (Boundary 진입 검증 최소 구현)        │
                  │     ▼                                     │
                  │  RED (T-U-002)                            │
                  │     ▼                                     │
                  │  GREEN ...                                │
                  └───────────────────────────────────────────┘
                           ║ (동기화 지점은 통합 REFACTOR 시)
                  ┌─ Logic Track ──────────────────────────────┐
                  │  RED (T-D-001)                            │
                  │     ▼                                     │
                  │  GREEN (MagicSquareValidator 골격)          │
                  │     ▼                                     │
                  │  RED (T-D-003, T-D-004)                   │
                  │     ▼                                     │
                  │  GREEN (행/열 합 판정)                       │
                  │     ▼                                     │
                  │  RED ...                                  │
                  └───────────────────────────────────────────┘
                                                    ▼
                                       [통합 REFACTOR]
                                       (두 트랙 모두 GREEN 상태에서만)
```

### 6.3 *병렬*의 의미 — 동시성 vs 격리성

| 오해 | 정확한 의미 |
|---|---|
| *"두 트랙을 한 RED 안에서 함께 검증한다"* | ✗ — 그것은 *통합 테스트*이며, Dual-Track의 RED가 아니다. |
| *"두 트랙을 시간상 동시에(같은 시각에) 작성한다"* | △ — 가능하지만 본질이 아니다. 본질은 *서로의 진행 속도에 무관*하다는 격리성. |
| *"두 트랙이 서로의 산출에 의존하지 않는다"* | ○ — Logic Track은 Boundary 없이 단독 GREEN, UI Track은 Domain Mock으로 단독 GREEN 가능. |

> ※ 즉, Dual-Track의 *병렬*은 *시간적 동시성*이 아니라 *논리적 격리성*이다.

### 6.4 학습자가 이 Step에서 부딪히는 *전형적 함정*

| 함정 | 등장 양상 | 처리 |
|---|---|---|
| *"GREEN을 통과시키려고 막 짜다 보니 코드가 더러워서 정리하면서 짰어요"* | GREEN 도중 동시 리팩토링 | 즉시 중단 후 *현재 RED만 통과*하는 코드로 되돌림. 정리는 REFACTOR 단계에서. |
| *"Boundary 테스트에서 실제 Domain을 호출하니 더 정확한 거 아닌가요?"* | 두 트랙의 격리성 위반 | Domain Mock으로 *위임 직전 검증*만 수행. 통합 검증은 `tests/integration/`(`T-I-XXX`)의 책무. |
| *"RED 작성하기 전에 production 코드부터 먼저 짜고 테스트는 마지막에..."* | RED 후행 (Anti-Persona A-2) | `03_프로젝트_규약_정의` `tdd_rules.red_phase.must_not` 직접 위반 — 작성 자체를 거부. |

> 엣지 / 입력 오류 / 조합 실패 케이스를 추가해 *변경 금지 영역(FR-1~FR-7)* 을 봉인.

### 7.1 6종 키 분석

| 키 | 내용 |

| **보호하는 Epic 목적** | **P4** (흐름 체화의 마지막 매듭), 그리고 **SC-1**(Domain 95%), **SC-2**(Boundary 100%), **SC-5**(Invariant 추적). |
| **보호하는 Invariant / 술어** | (a) D7(결정성)의 *반복 검증*, (b) D8(좌표 1-index 일관성), (c) D10(`E_UNSOLVABLE` 식별성), (d) FR-1~FR-7 변경 금지 영역 *전체*. |
| **위반 신호** | (a) 새 기능 추가 시 기존 테스트가 깨졌고, 그것을 *약화*시키려는 충동 (Anti-Persona A-5). (b) `xfail`/`skip`이 *근거 주석 없이* 추가됨. (c) 커버리지 미달 → `# pragma: no cover`로 *우회* 시도. (d) 표준 에러 메시지 byte-equal 테스트가 *문구만 살짝* 변경됨. |

### 7.2 회귀 보호 테스트의 3개 축

| 축 | 보호 대상 | 대표 테스트 ID |
|---|---|---|
| **엣지 (Edge)** | 경계값·회전·결정성 | `T-D-002`(회전), `T-D-008`(경계 셀), `T-D-009`/`T-D-023`/`T-D-051`(결정성 100회) |
| **입력 오류 (Input)** | 동시 위반 시 검증 순서·`locus` 안정성 | `T-U-040`~`T-U-042`(우선순위), `T-U-013`(첫 위반 좌표) |
| **조합 실패 (Domain)** | 두 조합 모두 비-마방진 식별 | `T-D-032`, `T-U-060`/`T-U-061`(코드 가림 금지), `T-I-014` |

### 7.3 *왜 이 Step이 한 번으로 닫히지 않는가*

- 회귀 보호는 *상태가 아니라 활동*이다. SC-1~SC-5는 *현재 시점의 측정값*이며, 코드 변경마다 다시 측정되어야 한다.
- 따라서 본 Step은 *완료*되는 것이 아니라 *현재 시점에 충족 상태로 외부화*되는 것이며, 이후 모든 변경에 대해 *다시* 통과되어야 한다.

## 8. Journey 전체에 걸친 횡단 관찰

### 8.1 단계별 *인지 부하*의 구성 변화

| Step | 주요 인지 부하의 종류 |
|---|---|
| Step 1 | *추상화* — 표면 정의를 부정하고 더 깊은 정의로 환원 |
| Step 2 | *정밀화* — 모호한 어휘를 byte-equal 진술로 환원 |
| Step 3 | *분해* — 인지 단위와 구현 단위를 *분리해서* 다룸 |
| Step 4 | *동기화* — 두 트랙의 격리성과 통합 시점의 균형 |
| Step 5 | *지속성* — *"끝"* 이 아니라 *"현재 시점의 통과"* 를 받아들임 |

> ※ 본 표는 *어느 Step에서 학습자가 가장 많이 막히는가*에 대한 진단 도구이다. 막힌 곳의 인지 부하 종류가 식별되면, 8.2의 회귀 정책으로 처리할 위치가 결정된다.

### 8.2 단계 회귀(Backtracking) 정책

> 본 Journey는 단방향이 *원칙*이지만, 일부 조건에서 *역행*이 허용된다. 역행은 *선행 단계의 합의 결함*을 의미하므로 비용이 크지만, 결함을 안고 전진하는 것보다는 항상 옳다.

| 발견 시점 | 발견된 결함 | 역행 대상 | 역행 비용 |
|---|---|---|---|
| Step 2 도중 | I1~I5 중 누락이 있음 | Step 1 | 낮음 (계약 작성 전이므로 영향 범위 최소) |
| Step 3 도중 | 어떤 Invariant가 *어느 서비스에 속하는지* 불명확 | Step 1 또는 Step 2 | 중간 (이미 작성된 계약 일부가 재진술될 수 있음) |
| Step 4 도중 | RED를 작성하다 *어느 Track에 속하는지* 모호함 | Step 3 | 중간 (Domain 분리 재합의) |
| Step 4 도중 | 표준 에러 메시지 한 글자 변경 필요 | Step 2 | 높음 (FR-5 변경 = 모든 의존 테스트 영향) |
| Step 5 도중 | 회귀 케이스가 *어떤 Invariant도 가리키지 못함* | Step 1 (혹은 새 D-x 정의) | 높음 (Invariant 자체의 누락이 뒤늦게 드러남) |

> ※ 역행 자체는 *실패가 아니다*. 결함을 안고 전진하는 것이 실패이다. 역행 사유는 *그 시점에 해당 Step의 산출물 끝에 기록*되어, 향후 같은 결함이 반복되지 않도록 외부화된다.

### 8.3 Anti-Persona 등장 → 처리 매트릭스

| Anti-ID | 가장 자주 등장하는 Step | 처리 |
|---|---|---|

## 마무리 진술

> 본 단계에서 우리가 도달한 결론은 다음과 같다.
>
> **"우리는 학습자의 머릿속에 있던 *시간의 흐름* 을 외부화했다.
> Level 1(Epic)이 *어떤 목적이 충족되어야 하는가*를 평면적으로 닫았다면,
> Level 2(본 단계)는 *그 목적이 어떤 순서로, 어떤 인지 부하의 변화를 통과하며 충족되는가* 를 시간 축 위에 다시 펼쳤다.
> 이 두 외부화의 결합은, 학습자가 같은 여정을 *다시 통과할 때*에도 *어디에서 막혔는지*를 식별 가능하게 만든다."**

본 Journey는 *1회 통과*만으로 닫히지 않는다. 동일 페르소나가 동일 Step을 *여러 번 통과*하면서, 매 통과에서 *Anti-Persona 신호의 등장 빈도*가 줄어드는 것이 본 학습 시스템의 본질적 성공 지표이다.
