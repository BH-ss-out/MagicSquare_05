## 1. 작업 목적

본 작업의 목적은 다음과 같다.

1. `01_문제_정의`에서 합의된 **불변 조건(I1~I5)** 과 `02_설계`에서 고정된 **계약/아키텍처 결정**을, *코드 작성 시점에 자동으로 강제*되도록 외부화한다.
2. Cursor AI가 본 프로젝트에서 코드를 생성·수정할 때, **TDD(Red-Green-Refactor) 흐름과 ECB(Entity-Control-Boundary) 경계**를 위반하지 않도록 사전 가드를 설치한다.
3. *"적절히/충분히"* 와 같은 모호한 표현을 배제하고, **각 규칙이 검증 가능한 형태**로 표현되도록 한다.

→ 즉, 본 산출물은 *"AI 코딩 보조에게 줄 지시문"이 아니라, 프로젝트의 합의된 헌법(constitution)을 YAML로 환원한 것*이다.

## 3. 핵심 설계 결정과 근거

본 절은 *"왜 그렇게 채웠는가"* 를 산출물 자체보다 더 길게 기록한다. 본 보고서의 학습적 가치가 여기에 있다.

### 3.1 `tdd_rules` 구조 변경 — `exit_condition` → `must_not`

- **변경 전**: 각 phase가 *"다음 단계로 가는 조건"* 만 기술 → **긍정 진술 중심**.
- **변경 후**: 각 phase가 *"이 단계에서 절대 하지 말 것"* 까지 기술 → **금지 진술까지 포함**.
- **근거**:
  - 긍정 진술만으로는 *"규칙에 명시되지 않은 행위는 허용된다"* 는 해석을 막을 수 없다.
  - 특히 `green_phase`의 흔한 위반은 *"테스트 통과 + 동시에 리팩터링"* 이며, 이는 `rules`로는 막기 어렵고 `must_not`로만 명시적 차단이 가능하다.
- → 즉, 본 변경은 **"허용 목록(allowlist)에서 허용+금지 이중 목록"으로의 격상**이다.

### 3.2 `architecture.layers.*.must_not` 신설

- 각 ECB 레이어에 *"무엇을 해야 하는가"* 와 함께 *"무엇을 하면 안 되는가"* 를 명시.
- **근거**: ECB는 *책임의 분리*가 아니라 *의존의 방향*에 의해 정의된다. 책임 진술만으로는 *"안쪽 레이어가 바깥 레이어를 import하는"* 위반을 막을 수 없다.
- 따라서 `entity.must_not = ["어떠한 외부 계층에도 의존하지 않는다"]` 같은 진술이 **검증 가능한 형태의 경계 정의**가 된다.

### 3.3 `forbidden`의 `pattern / reason / alternative` 3종 구조

- 단순 금지 목록이 아니라 *대안 제시*까지 의무화.
- **근거**:
  - "X 금지"만으로는 코드 작성자(또는 AI)가 *"그럼 무엇을 써야 하는가"* 에서 다시 자유 선택을 하게 된다 → 규칙의 결정성이 떨어진다.
  - `alternative`를 함께 박아두면, **금지가 곧 다음 행위 지정**이 되어 결정성이 회복된다.
- 예: `print()` 금지 → `logging` 사용 강제. *"디버그 출력을 어떻게 할지"* 가 더 이상 자유 선택이 아니다.

### 3.4 `ai_behavior.honesty` 절 신설

- *"테스트를 직접 실행하지 않은 상태에서 GREEN을 단정하지 않는다"* 와 같은 메타 규칙.
- **근거**: STEP 3의 검토에서 식별된 *"AI가 단독 검증할 수 없는 규칙"* 문제에 대한 직접 응답.
  - `tdd_rules.red_phase`의 *"실패를 눈으로 확인"* 은 AI가 도구 실행 없이는 충족 불가.
  - 이 한계를 *숨기지 않고 진술하도록* 강제하는 것이, 규칙을 거짓말로 우회하지 않게 하는 유일한 방법이다.
- → 즉, `honesty` 절은 *"규칙이 지켜졌는지에 대한 보고가 거짓이 되지 않도록 하는 메타 규칙"* 이다.

### 3.5 `file_structure`를 트리 다이어그램(블록 스칼라)으로 표현

- 표(table)나 리스트(list)가 아니라 ASCII 트리로 보존.
- **근거**:
  - 폴더 구조의 본질은 *"포함 관계"* 이며, 트리는 이 관계를 시각적으로 직접 표현하는 유일한 형식이다.
  - YAML의 `|` 블록 스칼라는 줄바꿈/들여쓰기를 보존하므로, 트리 그대로 저장 가능하다.
  - 주석(`# CLI entrypoint` 등)을 같은 줄에 둘 수 있어 *어떤 파일이 어떤 역할인지* 가 한눈에 드러난다.

## 4. 최종 산출물 구조 요약

```text
.cursorrules
├── project           # 정체성 (I1~I5 명시)
├── code_style        # 도구 + 스타일 가이드
├── architecture      # ECB 3계층 + 의존 방향

├── testing           # pytest + AAA + 80% + naming
├── forbidden         # 7개 항목 (pattern / reason / alternative)
├── file_structure    # ECB 폴더 트리 (블록 스칼라)
└── ai_behavior       # before / during / after / warnings / honesty
```

YAML 파서 검증: **통과** (`yaml.safe_load` OK).

## 6. 식별된 한계 및 다음 단계 함의

### 6.1 한계

1. **자동 강제력의 한계**: `.cursorrules`는 Cursor AI에 대한 *지시문*이지 정적 검증기가 아니다. 따라서 다음 도구가 함께 활성화되어야 실효성이 확보된다.
   - `Black` / `Ruff` (스타일·금지 패턴 검증)
   - `mypy --strict` (타입 힌트 강제)
   - `pytest --cov --cov-fail-under=80` (TDD/커버리지 강제)
   - import linter 또는 자체 스크립트 (ECB 의존 방향 검증)
2. **규약 vs. 도구의 이중화**: 동일 규칙이 `.cursorrules`와 `pyproject.toml` 양쪽에 표현될 가능성이 있다. 다음 단계에서 `pyproject.toml`을 작성할 때 *단일 진실 출처(SSOT)* 를 어디로 둘지 결정해야 한다.

### 6.2 다음 단계로의 함의

| 다음 단계 | 본 산출물이 부과한 제약 |
|---|---|
| RED 테스트 작성 | 테스트는 `tests/<layer>/test_<module>.py` 위치에, `test_<대상>_<상황>_<기대결과>` 패턴으로 작성. 각 테스트는 I1~I5 중 어느 것을 검증하는지 docstring/ID로 명시. |
| 구현(Implementation) | `entity` 먼저, `control`, `boundary` 순으로 안→밖. 각 함수는 타입 힌트·Google docstring 필수. `green_phase` 동안 리팩터링 금지. |
| 리팩터링 | 외부 동작 보존, 모든 테스트 통과 유지, 커버리지 ≥ 80% 유지. ECB 경계를 위반하는 방향의 구조 변경 금지. |

## 마무리 진술

> 본 단계에서 우리가 도달한 결론은 다음과 같다.
>
> **"우리는 코드를 짜기 위한 규칙을 만든 것이 아니다.
> 우리는 *무엇이 이 프로젝트에서 합의된 사실인가*를, 코드 작성 도구가 대신 강제해 줄 수 있는 형태로 환원했다."**

이 환원은 `01_문제_정의`의 *"암묵지를 형식지로 환원하는 능력"* 훈련의 직접적 연장선상에 있다.
즉, 본 작업은 *"도메인 규칙(I1~I5)"* 의 외부화에 이은 **"메타 규칙(개발 규약)의 외부화"** 이며, 다음 단계인 RED 테스트 작성은 이 두 외부화 위에서 비로소 결정적으로 수행될 수 있다.
